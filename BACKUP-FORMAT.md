# Hapag backup format 2

A user-selected ZIP contains `diary.json` and the referenced `photos/<sha256>.img` entries. It is a logical snapshot, not SQLite/WAL files. The JSON identifies `format: hapag-backup`, integer `version: 2`, creation time, foods/favorites, meals with independent food snapshots and integer-centavo cost, recipes with ingredient snapshots/yield, goals, water, and weight. Photo references are archive-relative, never device paths. Identical photo content is deduplicated. Temporary label images and unsaved drafts are excluded.

The complete database snapshot is read in a Room transaction. ZIP encoding, import, hashing and image bounds checks run on the IO dispatcher. Imports accept only the declared entry paths, forbid duplicate entries, require every photo reference to resolve and every photo to be referenced, verify photo SHA-256 and image bounds, validate record dates/IDs/ranges/uniqueness, and reject unsupported formats/versions. Integer fields reject fractional values. Limits: 16 MiB JSON, 25 MiB per photo, 256 MiB uncompressed archive, 10,000 photos and 50,000 records per collection. Export fails visibly if a saved attachment is missing rather than silently omitting it. ZIP CRC and hashes detect accidental corruption; these are not authenticity signatures or encryption.

A preview owns a private cache directory. Users review actual counts and explicitly confirm replacement, with an opportunity to cancel or back up their current diary first. Restoration copies photos into a new private immutable directory, flushes the file contents, and replaces database records in one transaction. The commit section is non-cancellable so coroutine cancellation cannot remove already-committed attachments. A failure rolls back records and removes only the new directory. Old photos are deliberately retained; repeated entries, prior drafts, and other references must be considered before future cleanup. Process termination before database commit leaves an unreferenced directory, not broken old records; after commit the new records reference already-written files. Hardware/filesystem failure is not a guarantee this application can make.

Preview survives activity recreation in the ViewModel. Process death requires selecting and checking the backup again; abandoned staging is in Android's cache and can be evicted. Source files and document-provider originals are never deleted by the reader. Creating a backup can leave a partial destination on failure; the app tells users to remove it and retry. The format is unencrypted; chooser-selected cloud providers manage their own connectivity and protection. Hapag still has no Internet permission.

Same-signer updates keep the existing local diary. A future production key cannot directly replace a debug-signed install; prove portable restore before changing the distribution/signing path. A backup is useful only if stored somewhere accessible after losing the app or phone.

Version 2 adds nullable integer `proteinGrams`, `carbsGrams` and `fatGrams` to goals. Each configured target must be 1–1,000 g; null means unset. Current imports accept versions 1 and 2. Missing macro-goal fields in version 1 import as unset while retaining the existing calorie, budget and water targets. App versions through v0.7 accept only backup version 1 and reject version 2; use the current app to restore new exports. The database upgrade to schema 3 is additive and preserves existing diary records.
